# 0029 — Pseudonymous users at the APIs

Builds on ADR 0022 (the kit and per-API tokens), 0024 (the catalog) and 0025 (Level 3). Closes the blueprint's
"pseudonymous `sub` in access tokens" item, for the APIs.

**Context.** Every token carried the user's Keycloak id as `sub`, so every API behind an MCP server, and every log
it writes, held the real id. An API is often another team's system; it needs a stable id per user (to filter, to
audit), not the identity provider's own. Keycloak's pairwise subject mapper gives a client a per-user pseudonym:
`UUID.nameUUIDFromBytes(sha256(sector + user id + salt))`, where the sector is the client's redirect URI host and
the salt is Keycloak's. A spike on the live realm settled the rest:

- On the kit server's client it works across the whole Level 3 path: the per-API token carries the pseudonym, the
  exchange and DPoP binding work, and the API's live check returns the same `sub` its token names.
- On a chat UI's client it breaks existing accounts. LibreChat binds an account to the token's `sub` and refuses the
  email fallback when it changes ("stored openidId does not match token sub"); Open WebUI does the same. A migration
  would rewrite rows inside each chat UI's own database.
- A client that signs no one in has no redirect URI, and Keycloak then refuses the mapper (no sector).
- A realm import leaves the salt empty (an admin create or update generates it). With an empty salt anyone knowing a
  user's Keycloak id could compute the pseudonym.

**Decision.**
- **Pseudonyms at the APIs only.** The catalog generator gives each kit server's client (the one that exchanges
  tokens for its API) a `pseudonymous subject` mapper with an empty salt, and an inert redirect URI,
  `http://<service>/`, whose host names the sector (the client's sign-in flows stay off). Each API sees its own
  stable pseudonym for each user; two APIs cannot join their logs, and none learns the Keycloak id. The chat UIs,
  the gateway and the MCP servers' audit lines keep the real id, so no chat UI account changes.
- **The salt is Keycloak's.** It is never in the realm file. `scripts/chat_ui_identity.py` (run by every `*-up`
  target and the lite profile) adds a missing mapper and, when it finds one with an empty salt (a fresh import),
  updates it once so Keycloak generates the salt. It never rewrites a mapper that has one: a new salt would rename
  every user at that API.
- **Re-identification is an identity administrator's act.** `make k3s-mcp-pseudonym WHO=<username>` prints the
  pseudonym each API sees for a user; `FIND=<pseudonym>` names the user behind one from an API's log. It needs
  Keycloak's admin access, reproduces Keycloak's algorithm with the stored salt, and never prints the salt.

**Verified** on the framework cluster: crm-api logged `7d183d3f…` and `ad13bc44…` for the analyst and the store
manager while crm-mcp's audit lines kept their Keycloak ids; the lookup named both; LibreChat sign-in and the lite
check were unchanged. On a fresh lite cluster the imported mapper came up without a salt, the identity step had
Keycloak generate one ("salt generated by Keycloak"), crm-api logged pseudonyms while crm-mcp kept the Keycloak ids,
and the lookup named the store manager behind crm-api's `2a192aeb…`.

**Consequences.** An API owner can audit per user without learning who the user is; the identity provider's
administrator can say who on request. Deleting the mapper (or its salt) renames every user at that API. Pseudonyms
for the chat UIs and the MCP servers stay possible: they need each chat UI account moved to the new id, a separate
decision.
