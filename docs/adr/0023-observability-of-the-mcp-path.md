# 0023 — Observability of the MCP path

Builds on ADR 0015 (the observability contract) and ADR 0022 (the MCP server kit).

**Context.** The MCP path (chat UI → MCP gateway → MCP server → identity provider → API) is where a mistake
or an attack shows up: refused tokens, tools outside a grant, refused exchanges, an API saying no. The
framework already has an OpenTelemetry-native contract and lab bundle (collector, VictoriaMetrics with
vmalert, Loki, Tempo, Grafana). The question was whether to keep it for the lightweight stack or move to
an all-in-one backend.

**Decision.**
- **Keep the ADR 0015 stack.** OpenTelemetry Collector (vendor-neutral, ADR 0011), VictoriaMetrics (lighter
  than Prometheus, same queries and rules), Loki, Tempo and Grafana with trace ↔ log ↔ metric links. An
  all-in-one backend would save a few pods but replace a working, documented contract; a platform that
  already runs its own stack only needs `observability/collector`, `dashboards` and `alerts`.
- **The kit reports for every server** (`mcp_kit.telemetry`), on the process's default Prometheus registry,
  served by the service's own `/metrics`: `mcp_kit_tool_calls_total{server,tool,outcome}`,
  `mcp_kit_tool_call_duration_seconds`, `mcp_kit_access_refused_total{server,reason}`,
  `mcp_kit_token_exchanges_total{server,outcome}` (issued, cached, refused),
  `mcp_kit_token_exchange_duration_seconds`, `mcp_kit_api_responses_total{server,status_class}`. Labels name
  servers, tools, outcomes and reasons only, never a tenant or a user (a test pins it).
- **Audit lines in the platform's log shape**: `ts`, `level`, `service`, `logger`, `msg` plus `trace_id` and
  `span_id` of the active span, then the decision's ids and outcome. The collector parses them like any log
  line, so Grafana opens an audit line's trace in Tempo. Refusals are `WARNING`.
- **One trace from the MCP server inwards**: the server's request span, its token exchange at Keycloak and its
  API call, and the API's own spans, joined by `traceparent` (the services' httpx instrumentation).
- **The MCP hop is correlated, not traced, for now.** The chat UI's and the gateway's MCP clients use
  `httpx2`, which no OpenTelemetry instrumentation covers, and LiteLLM records an incoming MCP trace context
  only as a span link. The framework does not patch third-party clients (no auto-instrumentation, ADR 0015),
  so a trace that starts in the chat UI ends at its MCP request; the MCP server starts the next one. They are
  joined by time, tool and pseudonymous subject in the audit lines. A client that sends `traceparent` joins
  the trace as is.
- **Open WebUI traces too** when the bundle is up: `make k3s-obs-up` sets its own `ENABLE_OTEL*` variables
  (gRPC to the collector) and `make k3s-obs-down` removes them; its model calls already join LiteLLM's spans.
- **A dashboard and three alerts.** "AI Circus · MCP servers" (generated by
  `scripts/generate_observability_dashboards.py`): calls, refusals, per-API tokens, latency, the API behind
  each server and the audit lines. Alerts: a spike in refused requests (possible probing), any refused token
  exchange, and a tool error rate above 20%.

**Consequences.** Every server built with the kit is observable without code of its own. The gap in the
MCP hop closes when the chat UI and LiteLLM propagate trace context on MCP calls; nothing else changes then.
